# CWE-798: Hard-coded Credentials

## What it is

Hard-coded credentials (CWE-798) are passwords, API keys, tokens, signing secrets or connection strings written directly in source code, for example `password="admin123"`, `API_KEY = "sk_live_..."` or `"postgresql://user:pass@host/db"`. Anyone who can read the code can read the secret: everyone with repository access, every clone and fork, the git history, build logs and the deployed package. The same secret is usually shared by every installation and cannot be changed without a new release. Scanners flag string literals assigned to names like `password`, `secret`, `token` or `key`, literal `password=` arguments, and strings that look like keys or credential URLs.

## How attackers exploit it

An attacker exploits hard-coded credentials simply by finding them. Public repositories are scanned by bots within minutes of a push, and leaked cloud keys and payment tokens are tried right away. Private code leaks through forks, backups, container images, decompiled packages, error pages and former staff. With a database password the attacker can read or change all the data; with an API key they can run up bills or send messages as the organisation; with a JWT or session signing secret they can forge a token for any user, including administrators. Removing the secret in a later commit does not help, because it stays in git history, so a leaked hard-coded credential must be revoked and replaced.

## How to fix it in Python

To fix hard-coded credentials, load the secret at runtime from the environment instead of the source file:

- Required secret: `os.environ["DB_PASSWORD"]`. A missing variable raises `KeyError: 'DB_PASSWORD'`, which is a clear failure.
- Friendlier message: `value = os.environ.get("DB_PASSWORD")`, then `if not value: raise RuntimeError("DB_PASSWORD is not set")`.
- Never use the real secret as a default: `os.environ.get("API_KEY", "sk_live_...")` is still hard-coded.
- Credential-bearing connection strings come from one variable such as `DATABASE_URL`.
- Cloud SDKs such as boto3 read keys from environment variables, config files or an IAM role on their own; just remove the explicit key arguments.
- Use descriptive variable names and list them (without values) in the README or a `.env.example`.
- Tests can set the variable with `monkeypatch.setenv`.
- After the fix, the leaked secret must be rotated, because it remains in git history.

## Unsafe example

This hard-coded credentials example puts the database password in the source code:

```python
import psycopg

def connect_db():
    return psycopg.connect(
        host="db.internal",
        dbname="hr",
        user="hr_app",
        password="FAKE_pass_123",
    )
```

Everyone who can see this file, its git history or the deployed package now has the password. Development, testing and production all share it, and changing it requires editing code and redeploying. The same problem applies to API keys, JWT secrets and URLs like `postgresql://user:pass@host/db`.

## Safe example

The hard-coded credentials fix reads the secret from an environment variable and fails clearly if it is missing:

```python
import os
import psycopg

def connect_db():
    password = os.environ.get("HR_DB_PASSWORD")
    if not password:
        raise RuntimeError("HR_DB_PASSWORD environment variable is not set")
    return psycopg.connect(
        host="db.internal",
        dbname="hr",
        user="hr_app",
        password=password,
    )
```

The function name, parameters and return value are unchanged; only the source of the password moved. The deployment sets `HR_DB_PASSWORD` (or a secrets manager injects it). Non-secret settings such as the host name can stay in code.

## Common wrong fixes

These changes look like hard-coded credential fixes but still leak the secret:

- Using the secret as a fallback: `os.environ.get("API_KEY", "sk_live_FAKE123")`.
- Base64-encoding, reversing or splitting the string; it is still recoverable from the code.
- Moving the secret to another `.py` file or a committed config file.
- Renaming the variable (`pw` instead of `password`) so the scanner stops matching.
- Replacing the secret with an empty string, which silently breaks login or makes it accept anything.
- Encrypting the secret with a key that is also in the code.
- Adding `# nosec`, or deleting the function that needs the credential.

## Checklist for a correct fix

Before accepting a hard-coded credentials fix, confirm:

- No password, key, token or credential-bearing URL remains as a string literal, including as a default value.
- The secret is read from `os.environ`, or from the SDK's own credential chain.
- A missing secret fails clearly (`KeyError` from `os.environ[...]`, or a `RuntimeError` naming the variable), not with a silent empty value.
- The environment variable name is descriptive, such as `ALERT_SMTP_PASSWORD`.
- The function keeps its name, parameters and normal behaviour when the variable is set.
- Only `import os` is added; no new third-party packages and no `# nosec`.
- The leaked secret is flagged for rotation.
