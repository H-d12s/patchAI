# CWE-327: Broken or Risky Cryptography

## What it is

Broken or risky cryptography (CWE-327) means using an algorithm that is too weak for the security job it does. In Python the usual cases are `hashlib.md5` or `hashlib.sha1` for storing passwords, signing messages or building tokens; fast hashes (even SHA-256) without a salt for passwords; homemade signatures like `md5(secret + data)`; and the `random` module (`random.random`, `random.choice`, `random.randint`) for session IDs, reset tokens or one-time codes. The related CWE-328 and CWE-330 cover weak hashes and predictable random values. MD5 and SHA-1 have practical collision attacks, fast hashes are brute-forced on GPUs, and `random` is a predictable generator that was never meant for secrets.

## How attackers exploit it

An attacker exploits weak cryptography by doing work the developer assumed was impossible. A stolen table of unsalted MD5 or SHA-1 password hashes is cracked with precomputed tables and GPU guessing at billions of attempts per second, revealing most real passwords within hours, and identical passwords share the same hash. MD5 collisions let an attacker create two different files or messages with the same hash, and `md5(secret + message)` signatures are open to length-extension forgery. Tokens built with `random`, timestamps or user data can be predicted: the Mersenne Twister state can be rebuilt from enough outputs, and `sha1(email + time)` is reproduced by trying nearby timestamps. Comparing secrets with `==` can also leak them through timing.

## How to fix it in Python

To fix weak cryptography, use the standard-library tool that fits the job:

- Passwords: `hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)` or `hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)`, with a new `salt = secrets.token_bytes(16)` per password. Store the salt with the hash, e.g. `salt.hex() + "$" + digest.hex()`.
- Verifying passwords: recompute with the stored salt and compare with `hmac.compare_digest`.
- Message signatures: `hmac.new(key, msg, hashlib.sha256).hexdigest()`, checked with `hmac.compare_digest`.
- Integrity checks and fingerprints: `hashlib.sha256(data).hexdigest()`.
- Tokens, session IDs, reset links, API keys: `secrets.token_urlsafe(32)` or `secrets.token_hex(20)`. Numeric codes: `secrets.randbelow(1_000_000)`. Random picks: `secrets.choice`.
- `usedforsecurity=False` is only for non-security uses such as cache keys.
- Changing a stored hash or signature format means existing data must be migrated.

## Unsafe example

This weak cryptography example stores passwords as unsalted MD5 and makes reset tokens with `random`:

```python
import hashlib
import random

def hash_password(password: str) -> str:
    return hashlib.md5(password.encode("utf-8")).hexdigest()

def make_reset_token() -> str:
    return str(random.randint(100000, 999999999))
```

MD5 is fast and unsalted, so a leaked table is cracked quickly and users with the same password get the same hash. The `random` module is predictable and the token range is small, so an attacker can guess valid reset tokens.

## Safe example

The weak cryptography fix uses a slow, salted key-derivation function and a constant-time comparison:

```python
import hashlib
import hmac
import secrets

def hash_password(password: str) -> str:
    salt = secrets.token_bytes(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)
    return salt.hex() + "$" + digest.hex()

def verify_password(password: str, stored: str) -> bool:
    salt_hex, digest_hex = stored.split("$", 1)
    salt = bytes.fromhex(salt_hex)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)
    return hmac.compare_digest(digest.hex(), digest_hex)
```

The reset token becomes `return secrets.token_urlsafe(32)`. Function names, parameters and return types stay the same. Old MD5 hashes must be migrated, for example by re-hashing at the user's next successful login or forcing a reset.

## Common wrong fixes

These changes look like weak cryptography fixes but are still unsafe:

- Swapping MD5 for SHA-1 or plain SHA-256 for passwords. They are still fast, and unsalted.
- Adding one fixed, hard-coded salt shared by every user.
- Hashing several times in a loop or inventing a custom scheme instead of PBKDF2 or scrypt.
- Passing `usedforsecurity=False` to silence the scanner while the hash still protects passwords, tokens or signatures.
- Seeding `random` with the time or `os.urandom`; the generator is still predictable.
- Comparing hashes or signatures with `==` instead of `hmac.compare_digest`.
- Treating base64 or XOR as encryption.
- Adding `# nosec` or wrapping the code in try/except.

## Checklist for a correct fix

Before accepting a weak cryptography fix, confirm:

- Passwords use `hashlib.pbkdf2_hmac` (SHA-256, at least 600,000 iterations) or `hashlib.scrypt`, with a fresh `secrets.token_bytes(16)` salt stored next to the hash.
- Signatures use `hmac` with SHA-256, and hash or signature comparisons use `hmac.compare_digest`.
- Integrity checks use `hashlib.sha256` or stronger.
- Tokens, codes and IDs come from `secrets`, not `random`.
- No MD5 or SHA-1 remains for a security purpose, and `usedforsecurity=False` does not hide one.
- The function keeps its name, parameters and return type; if a stored or transmitted format changes, the note says existing data or clients must be updated.
- Only stdlib imports (`hashlib`, `hmac`, `secrets`) are added; no `# nosec`.
